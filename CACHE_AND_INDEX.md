# Кэш и глобальный фотоиндекс — v22 (ленивый режим)

## Главный принцип

Глобальный поиск используется редко, поэтому его индекс **не обслуживается в фоне во время обычной работы Mini App**.

Ни запуск приложения, ни возврат из нативного VK сами по себе больше не запускают `photos.getAll` и не перечитывают dirty-альбомы ради глобального поиска. Индекс приводится в порядок только тогда, когда пользователь реально открывает глобальный поиск, либо вручную запускает диагностическую синхронизацию.

Это означает: если глобальным поиском не пользоваться месяц, глобальный индекс не создаёт за этот месяц ни одного фонового API-запроса.

## Что где хранится

### localStorage — быстрый UI-кэш

Префикс: `vk-photo-manager:v5:`.

Здесь остаются:
- список альбомов;
- индекс названий альбомов;
- последние фотографии открытых альбомов;
- комментарии и ленты комментариев.

Целый большой альбом в localStorage не сохраняется: для одного альбома сохраняется максимум 60 первых фотографий. Кэш старше 7 суток удаляется, а при переполнении localStorage автоматически удаляются самые старые UI-снимки.

### IndexedDB — постоянный глобальный индекс фотографий

База: `vk-photo-manager-photo-index`.

В ней сохраняются компактные записи:
- `id`;
- `owner_id`;
- `album_id`;
- дата;
- описание;
- нормализованный текст для поиска;
- один URL подходящего превью.

Полные объекты VK, лайки, комментарии и все размеры изображения в глобальном индексе не хранятся.

## Ленивое обновление глобального индекса

### Если полного индекса ещё нет

При первом реальном открытии глобального поиска строится полный индекс через `photos.getAll`. Для ~11 000 фотографий это около 55 страниц по 200 фото.

### Если индекс уже есть

Поиск сразу начинает работать по IndexedDB. Затем, только внутри экрана глобального поиска, выбирается один из режимов:

1. **dirty-only** — индекс достаточно свежий: синхронизируются только альбомы, которые были помечены как изменённые нативными действиями VK. Для `photos.get` используется страница до 1000 фото, поэтому большинство обычных альбомов сверяются одним запросом. Если dirty-альбомов нет, для глобального индекса не выполняется ни одного API-запроса.
2. **quick** — быстрая проверка новых фотографий через начало `photos.getAll`. Она выполняется не чаще одного раза в 30 минут и обычно требует 1 запроса.
3. **full** — полная сверка всего индекса, если последняя полная синхронизация старше 7 суток, индекс отсутствует/неполный либо пользователь нажал принудительное обновление.

Важно: порог 7 суток считается только при открытии глобального поиска. Нет фонового таймера, который сам запускает полную сверку через 7 суток.

Во время полной сверки старый готовый индекс продолжает использоваться для поиска до атомарной замены новым.

## Нативные действия VK

До ухода в нативный VK приложение заранее инвалидирует соответствующий UI-кэш и, где требуется, записывает persistent dirty-метку альбома.

Обрабатываются:
- загрузка фото в альбом;
- копирование фото через нативную загрузку;
- удаление фото;
- удаление альбома;
- добавление/ответ на комментарий.

Dirty-метки лежат в localStorage отдельно от UI-кэша и переживают выгрузку WebView. После возврата из нативного VK они **не заставляют глобальный индекс немедленно обращаться к API**. Они спокойно ждут следующего открытия глобального поиска.

При этом обычный интерфейс альбома может, как и раньше, перечитать открытую страницу фотографий после нативной загрузки/удаления — это обновление текущего UI, а не фоновое обслуживание глобального поиска.

Для нативного удаления одной фотографии остаётся точная проверка `photos.getById`, потому что она нужна и интерфейсу: понять, действительно ли фото было удалено и нужно ли закрыть просмотр. Если результат известен, IndexedDB обновляется попутно без полной перестройки.

## Изменения внутри Mini App

Они не требуют дополнительных API-вызовов для индекса:

- изменение описания немедленно обновляет запись IndexedDB;
- перемещение фото немедленно меняет `album_id` в IndexedDB;
- подтверждённое локальное удаление удаляет одну запись;
- при гонке с полной синхронизацией локальные подтверждённые изменения повторно накладываются поверх нового серверного снимка.

## Диагностика

Статус индекса:

```js
await vkPhotoIndexDebug.status()
```

План, который будет выбран при следующей обычной синхронизации поиска:

```js
await vkPhotoIndexDebug.plan()
```

Возможные `mode`:
- `dirty-only`;
- `quick`;
- `full`.

Принудительная быстрая синхронизация:

```js
await vkPhotoIndexDebug.sync()
```

Принудительная полная сверка:

```js
await vkPhotoIndexDebug.fullSync()
```

Синхронизация только dirty-альбомов:

```js
await vkPhotoIndexDebug.syncDirty()
```

Счётчики обращений к VK API:

```js
vkApiDebug.stats()
```

Сброс счётчиков:

```js
vkApiDebug.reset()
```

## Практическая проверка после публикации

### 1. Проверка отсутствия фоновой работы

1. Запустить Mini App, **не открывая глобальный поиск**.
2. Выполнить `vkApiDebug.reset()` после обычной загрузки интерфейса.
3. Немного поработать с альбомами либо просто оставить приложение открытым.
4. Проверить `vkApiDebug.stats()`.

Не должно появиться `photos.getAll` только из-за существования глобального индекса.

### 2. Первое построение

1. Открыть глобальный поиск впервые.
2. Дождаться готового индекса.
3. Проверить `await vkPhotoIndexDebug.status()`.

Ожидается:
- `countMatchesMeta: true`;
- `malformed: 0`;
- количество близко к фактическому числу фотографий VK.

### 3. Повторное открытие

1. Выполнить `vkApiDebug.reset()`.
2. Закрыть и снова открыть глобальный поиск в течение 30 минут.
3. Проверить `vkApiDebug.stats()`.

Если dirty-альбомов нет, `photos.getAll` должен быть `0`.

### 4. Нативная загрузка

1. Загрузить фото через нативный VK.
2. Вернуться в Mini App.
3. Выполнить `await vkPhotoIndexDebug.status()` — соответствующий альбом может остаться в `dirty`.
4. Это нормально: глобальный индекс специально не синхронизируется сразу.
5. Открыть глобальный поиск — dirty-альбом должен синхронизироваться, после чего новая фотография должна находиться.

### 5. Нативное удаление

Удалить фото через штатный VK и вернуться. Точная проверка фото может сразу обновить одну запись индекса. Если точная проверка не удалась, dirty-метка должна остаться до следующего глобального поиска.

### 6. Проверка старого индекса

Для контроля политики можно посмотреть:

```js
await vkPhotoIndexDebug.plan()
```

Индекс старше 7 суток должен дать `mode: "full"`. Более свежий индекс с просроченной быстрой проверкой — `mode: "quick"`. Свежий индекс — `mode: "dirty-only"`.

### 7. Контрольная полная сверка

В любой момент:

```js
await vkPhotoIndexDebug.fullSync()
await vkPhotoIndexDebug.status()
```

После успешной полной сверки `countMatchesMeta` должен быть `true`, `malformed` — `0`.

## v21: скорость открытия фотографий

Глобальный IndexedDB-индекс по-прежнему обслуживается только при открытии глобального поиска и не участвует в обычном открытии фотографии.

В viewer изменён только визуальный путь загрузки изображения:

1. При клике сразу используется маленький URL превью (тот же тип URL, который уже загружался в карточке альбома).
2. Максимальный размер фотографии загружается параллельно через `Image()`.
3. После загрузки большой версии preview незаметно заменяется на неё.
4. Повторный `renderPhotoHeader()` после `photos.getById` не запускает второй одинаковый preload.
5. При ошибке большого файла уже показанное preview остаётся на экране.

Для измерения в консоли:

```js
photoViewerDebug.last()
```

`previewMs` — время от клика до установки быстрого preview; `highResMs` — время до готовности максимального размера.

## v22: чёткие обложки альбомов

Раньше `getAlbumCover()` выбирал минимальную обложку примерно от 200 px. Карточки альбомов заметно шире фото-карточек, поэтому на больших экранах и экранах с высокой плотностью пикселей такая обложка могла растягиваться и выглядеть размытой.

В v22 для обложек формируется `srcset` из доступных размеров VK. Браузер сам выбирает изображение под фактическую ширину карточки и `devicePixelRatio`. Резервный `src` ориентирован на 640 px. Сам глобальный фотоиндекс и его ленивый режим этим изменением не затрагиваются.

## v23: облегчённые миниатюры фотографий

- Геометрия сетки фотографий не изменена.
- Обложки альбомов возвращены к прежнему выбору около 200 px.
- Для миниатюр фотографий внутри альбома целевой размер снижен с 200 до 130 px.
- При открытии фотографии viewer по-прежнему загружает качественную большую версию; изменение касается только сетки альбома.
